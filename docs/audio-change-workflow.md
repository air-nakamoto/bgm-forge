# 音の調整から公開までの進め方

更新: 2026-09-23。今回の音色バランス調整の経緯と、次回も使う手順。

## 今回の経緯

1. 編集後の旋律・伴奏バランスを、夜空・儀式・和風×オルゴール・合唱・箏×2seedの18条件で計測した。
2. 同じ楽譜から旋律と伴奏を分離し、A（現行相当）とB（伴奏を保ち旋律を下げる候補）を9組作成した。
3. ユーザーが夜空×オルゴールのBを聴き、「Bちゃんとメロディ音量下がったのでいいと思います」と採用した。
4. この時点では比較音源しか変わっておらず、本体には未反映だった。「採用」と「実装」を区別して説明できず、公開できるかのやり取りで混乱が起きた。
5. 本体の夜空×オルゴール・旋律ありに限定してB方式を実装した。補正前のミックスから増幅量を決め、旋律を下げた後は再正規化しない。
6. Chromeで本体出力と採用Bを比較し、最大差は16bit PCMで1段階、ピーク0.10271835。既存回帰テストも全PASS。
7. 単体版・読込ハッシュ・MDを更新し、`2c805e6` にコミット。公開コマンドはこの作業では実行しておらず、公開サイトへの適用確認は未実施。

計測詳細は [音色バランス監査](balance-audit-20260923.md)。ローカル比較音源は `Claude outputs/balance-20260923/`。

## 次回の手順

1. **再現と計測**：場面・音色・seed・テンポ・指定尺・旋律設定・新規/編集を記録する。譜面と実音を分けて測る。
2. **比較音源**：同じ楽譜と条件でA/Bを作り、どのパート・増幅量を変更したか明記する。全体音量が違う場合も伝える。
3. **試聴と採用範囲**：人間に鳴らして確かめてもらい、どの組合せが採用されたか残す。1例の採用を全音色の承認へ広げない。
4. **本体実装**：採用済みの範囲を反映する。比較WAVだけを変更した状態で「本体反映済み」と言わない。採用された作業は再確認を繰り返さず進める。
5. **再検証**：採用音源との一致・数値・既存機能・対象外への影響を確認する。テストPASSの範囲と聴感の判断を分ける。
6. **配布物と記録**：読込ハッシュ更新、単体版再生成、必要なテスト、HANDOVER更新、日本語コミットまで済ませる。
7. **公開**：`公開する.command` の実行と成功確認を別の段階として扱う。コミット済みは公開済みを意味しない。再読み込み後、新しく生成した曲で確認する。

## 状態の伝え方

## MDを更新するタイミング

音の調整に限らず、開発全般で以下のタイミングを使う。作業終了時にまとめて思い出すのではなく、判断・状態が変わった時点で記録する。

| タイミング | 更新するMD | 記録する内容 |
|---|---|---|
| 着手・方針決定 | HANDOVER §6.0、関連する計画MD | 目的、対象範囲、成功条件、未確認事項。提案と決定済み仕様を区別する |
| 再現・計測完了 | docs内の調査MD、HANDOVER §3 | 再現条件、seed、測定方法、数値、ソースの版、判明した原因と測定の限界 |
| A/B作成・試聴依頼 | 調査MD、HANDOVER §0 | 比較音源の場所、A/Bの差、試聴してほしい点。「候補作成済み・本体未反映」と明記する |
| ユーザーが採用・却下 | 調査MD、HANDOVER §0・§6.0 | 判断日、発言の要旨、採用した条件・範囲、次の実装。未実装ならその状態を維持する |
| 実装・検証完了、コミット前 | HANDOVER §0・§3・§6.0、関連MD、必要ならREADME | 最終仕様、変更前後の数値、テスト結果、未検証範囲、単体版更新、公開未確認。コードと対応するMDを同じコミットへ入れる |
| 公開実行後 | HANDOVER §0・§3 | 対象コミット、日時、実行結果、サイトでの確認範囲。実行成功と実際の動作確認を区別する |
| 中断・引き継ぎ | HANDOVER §0・§6.0 | 完了箇所、未完了箇所、未コミット差分、再開する具体的な一手 |

流れは **方針を記録 → 計測を記録 → 試聴候補を記録 → 採否を記録 → 実装・検証とMDを同時コミット → 公開結果を記録**。

### 更新時の整合性チェック

- 現状の入口はHANDOVER §0、計測履歴は§3、次の作業は§6.0、詳細な根拠はdocsに置く。概要から詳細へリンクする。
- 現行仕様の説明は置き換え、過去の計測結果は当時の条件・日付を付けて残す。「最新の追記」だけで矛盾を放置しない。
- 関連MDを検索し、「未実装」「採用済み」「公開済み」、数値、適用範囲に食い違いがないか確認する。利用者向け仕様が変わった場合はREADMEも更新する。
- PASSは実行した検査の範囲で記載する。未実施の試聴・実機・公開確認を完了扱いにしない。
- コミット前に `git diff --check` と差分・リンク先を確認する。文書だけの更新なら、音声コード未変更と分かる記録にする。
- 作成中コミットのハッシュを同じコミットへ書こうとしない。必要なら確定後の記録に追記する。公開結果のMDは公開後の文書コミットにでき、アプリ本体の再公開とは分けて扱う。

## 状態を報告するとき

「比較音源作成済み」「試聴で採用」「本体実装済み」「単体版更新済み」「コミット済み」「公開確認済み」を区別する。
公開ログやサイト確認がない場合は「公開未確認」と書く。ユーザーの操作ミスと断定する前に、編集経路と実際の生成データを調べる。

## 今回の適用範囲と残課題

- 本体適用済み：夜空×オルゴール・旋律あり。旋律RMSが伴奏を上回る場合だけ減音し、伴奏を維持する。
- 他の場面・音色、合唱・箏にはこの補正を一律適用していない。
- 対象は2回のレンダリングを行うため処理時間・メモリが増える。長尺・プレビュー・複数seedでの聴感と負荷検証が残る。
- RMSの一致は知覚音量の一致ではない。採用の根拠はユーザーの試聴であり、数値だけで音質向上を断定しない。
